## Architecture Overview

- 扩展无打包工具：所有脚本挂在 `globalThis.LT` 上，manifest 里 content_scripts 的注入顺序就是依赖顺序；Service Worker 用 `importScripts`；popup / options 用 `<script>` 标签。
- 三个执行环境：
  - `src/main-world/page-bridge.js` 跑在 YouTube 页面的 MAIN world（document_start），能拿 `movie_player.getPlayerResponse()`，能包住 `window.fetch` / XHR；不能用 chrome.* API，只能 `window.postMessage` 和内容脚本通信。
  - 内容脚本（隔离世界）承载全部会话状态：直播会话在 `src/content/main.js`，整片字幕任务在 `src/content/video-subs.js`。
  - `src/background/service-worker.js` 只做轻活：默认设置、角标、快捷键、以及新增的文字模型请求转发（流式端口）。MV3 SW 空闲 30 秒会被杀、单请求超 5 分钟会被杀，所以不在 SW 里放任务状态。
- 整片字幕数据流：`YouTube.captionTracks()` → 选轨 → `YouTube.fetchCaptions()`（页面桥读 json3）→ `Json3.parse` → `Segmenter.build`（单元 = 编号 + 起止 + 原文）→ `Chunker.plan` 分块 → worker 按当前播放位置 `Chunker.pick` 取块 → `TextModel.translate`（经 `Net.post` 直连或转发）→ `Chunker.parseResponse` / `validate` → 填 `texts[]` 并 `SubsCache.setChunk` → `tick()` 每 200ms 用 `SubsScheduler.indexAt` 挑当前条 → `CaptionLayer.showTimed`。
- 两种模式共用 `CaptionLayer`、场景 / 语言 / 背景设置和提示词围栏结构；直播开始时调用 `videoSubs.deactivate()`，整片字幕开始时先 `stop()` 直播。

### Key Patterns Discovered

- **generation + alive() 作废旧异步**：直播会话和整片字幕任务都用递增的 generation，每个 await 之后检查 `alive()`（generation 未变且 videoId 未变），旧回调绝不能改新状态。测试里专门覆盖了取消和换视频。
- **开始时冻结配置快照**：任务开始时读一次 settings 组成 config / system prompt / 指纹，运行中改设置不影响本次。
- **不可信资料围栏**：视频标题简介和用户背景包在 `<session_context>` 里，之后重申任务；`buildSubs` 沿用了这个结构，别简化。
- **模型只见编号和文字**：时间轴永远由程序回填，这是从参考项目 D:\gemini-asr-correction 学来的经验（那边让模型重抄 SRT 时间轴出过错）。
- **Node 自检方式**：纯逻辑模块直接 `require`（它们只往 globalThis.LT 挂东西）；带浏览器依赖的用 `vm.createContext` 注入 stub（见 tools/lifecycle.test.js 和 tools/video-subs.test.js 的 harness）。
- **注释与提交说明用中文**，主 README 英文、中文 README 对应。
- **版本号四处同步**：manifest.json、package.json、两份 README 的版本行与下载文件名、CHANGELOG；tools/check.js 校验 manifest 与 package 一致。

## Decisions Made

| Decision | Options Considered | Rationale |
|----------|-------------------|-----------|
| 首版只用 YouTube 自带字幕轨，不做转写 | 转写模型（用户原始想法）/ 自带字幕 | 浏览器里拿不到比实时快的整片音频；下载音频流要解签名 + pot，等于维护 yt-dlp；转写要另立项先解决音频来源 |
| 任务跑在内容脚本，不用 offscreen + IndexedDB | GPT 方案是 offscreen 承载 Worker + 扩展 IndexedDB | 个人工具，用户在页面上等；页面在任务就在，换页取消但已完成块已落盘；少一个执行环境和一整套消息转发 |
| 缓存用 chrome.storage.local + unlimitedStorage，按块独立键 | IndexedDB / 整片一个键 | 内容脚本直接读写；按块写避免并发互相覆盖和每次重写整片 |
| 从当前位置优先、翻好即显示，不等整片 | GPT 原方案「全部完成才启用」 | 三小时回放按块估算要 6–12 分钟，与用户「等十几二十秒」的预期不符 |
| 自动字幕按词级时间重切，用估算停顿 | 按播放器显示行 1:1 翻 / 原样搬参考项目的 1.2 秒 + 40 字 | 日语谓语在句尾，按显示行翻出半截中文；json3 只有词起点没有终点，只能估算，阈值放宽 |
| 输出格式 `编号<TAB>译文` 逐行 + 整集合校验 | JSON 模式 | 各家兼容接口 JSON 支持不一；校验编号全集、空译文、结束原因，不只看最后一个编号 |
| 直连优先、失败转 SW 流式转发；自定义域名走 optional_host_permissions | 全部走 SW / 全部直连 | Gemini、OpenAI 官方接口允许跨域；第三方不一定；SW 有 30 秒 / 5 分钟限制，流式能避开 |
| 配置变化不自动重翻，旧完整缓存照用并标注 | 自动重翻 | 不悄悄消耗额度；「重新翻译」是显式操作且弹窗二次确认 |
| 两模式在同一页面互斥 | 并存 | 共用字幕层和状态提示位，并存会互相覆盖 |
| 分句规则版本进指纹和原文缓存有效性 | 不管 | 改分句后编号对不上旧译文 |

## Assumptions Made

- Gemini generateContent 与 OpenAI 官方 chat/completions 允许来自 www.youtube.com 页面的跨域请求（用户用 GPT 做过无 Key 预检，带 Key 的真实请求未验）
- YouTube 播放器加载字幕时经过 window.fetch 或 XMLHttpRequest，且发生在我们 document_start 装钩子之后
- json3 自动字幕的 `segs[].tOffsetMs` 是词级起点偏移（没有终点，按字符数估算发音时长：CJK 每字 150ms、其他每字符 65ms）
- `player.getPlayerResponse().captions.playerCaptionsTracklistRenderer.captionTracks` 结构未变，`kind === 'asr'` 表示自动字幕
- 内容脚本发起的 fetch 不受页面 CSP 限制（现有 WebSocket 同理已在用）
- Chrome 允许在 optional_host_permissions 覆盖范围内申请带端口的 origin 模式（有不带端口的回退）

## Potential Gotchas

- 直播 `start()` 一开始就调 `videoSubs.deactivate()`，直播页自动开始时也会跑到，属预期；整片字幕 `start()` 会先 `stop()` 直播。
- `main.js` 的 `stop()` 现在会 `caption.setVisible(true)`：原来广告期间停止直播会让字幕层一直隐藏，整片字幕接着用会看不见。
- 弹窗只在 `status.onWatchPage && !status.isLive` 时显示整片字幕区块；正在直播的页面看不到它是预期。
- `tools/video-subs.test.js` 的 harness 把 `LT.Json3.parse` 和 `LT.Segmenter.build` 换成直通 stub，并把 `LT.SUBS.BACKOFF_MS` 改成 1；lifecycle 测试需要 `LT.VideoSubsController` stub，改 main.js 对控制器的调用时记得同步 stub。
- `finish()` 现在 `await` 元信息写入，`start()` 返回时 complete 标记已落盘；测试依赖这一点。
- 「含当前位置的块」会拆成 头段 → 其余 → 位置之前 三次请求，所以从头开始播时第一块是两次请求；写断言要考虑这一点。
- `Chunker.parseResponse` 解析用未 trim 的原始行匹配，「4<TAB>」这种空译文行会被记成缺失而不是接到上一条；纯数字行同理。
- 缓存管理里 `keysOf` / `clearAll` / `bytesInUse` 用 `storage.get(null)` 读全部数据，只应在手动操作时调用。
- `optional_host_permissions` 只对 SW 转发有意义；页面直连由 CORS 决定，与 host 权限无关。
